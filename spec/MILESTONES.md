# MILESTONES – אתר TODO List משותף

**מסמכי מקור:** `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md`  
**מטרה:** חלוקת פיתוח האתר ל-Milestones ניתנים לבדיקה ולאישור, בדגש על Vertical Slices.

## כללי ביצוע הפיתוח – Development Execution Rules

1. יש לפתח את ה-Milestones **לפי הסדר** המופיע להלן. אין לדלג על אבן דרך או להתחיל אבן דרך מאוחרת טרם אישור קודמתה.
2. בסיום כל Milestone יש **לעצור את הפיתוח**, להציג למשתמש את התוצר העובד, לפרט אילו בדיקות בוצעו ולהציג את תוצאותיהן מול כל סעיף ב-**Definition of Done**. יש לציין במפורש כל בדיקה שלא בוצעה או כל תנאי שלא הושלם.
3. **אין להתחיל בפיתוח ה-Milestone הבא ללא אישור מפורש של המשתמש.** תיקונים הנדרשים לצורך עמידה ב-Definition of Done שייכים לאותה אבן דרך.
4. אין להוסיף פיצ'רים או לשנות את ה-PRD, ה-ARCHITECTURE או ה-DESIGN ללא אישור. כאשר יש סתירה בין דוגמאות חזותיות לבין הדרישות, יש לפעול לפי סדר הקדימויות שב-`DESIGN.md`.
5. כל Milestone יותיר את מה שכבר פותח במצב עובד וניתן לבדיקה; יש לבצע בדיקות רגרסיה מתאימות על היכולות הקודמות.

## Milestone 1 – יסודות המערכת וצפייה ברשימה משותפת 🟢

**שם ומטרה:** הקמת מוצר Web נגיש דרך כתובת ציבורית, שמציג רשימת משימות מתוך Database אמיתי; זהו Slice ראשון מקצה לקצה, עם תשתית לפריסה ולהמשך CRUD.

**מה יש לממש:**
- Repository יחיד ב-GitHub; פרויקט React + TypeScript + Vite, ניווט לשני הנתיבים `/` ו-`/about`, CSS בסיסי בעברית RTL, כולל פריסה Responsive: שני אזורים זה לצד זה בדסקטופ, ועמודה אחת (רשימה מעל פרטים) במובייל.
- שני פרויקטי Supabase PostgreSQL, **Dev** ו-**Production**, עם `tasks` ו-Constraints בהתאם ל-`ARCHITECTURE.md`; Database Migrations ב-Git: מוחלות על Dev במהלך הבנייה באמצעות Supabase CLI, ועל Production אוטומטית בעת Push דרך Supabase GitHub Integration (לפי `ARCHITECTURE.md`, ADR-1), והפרדה מאובטחת של פרטי הגישה.
- Vercel Functions ב-Node.js/TypeScript, חיבור מאובטח דרך Pooler ו-`GET /api/tasks` שמחזיר נתונים לפי `position`.
- דף הבית עם Header וניווט, רשימת משימות בצד ימין ואזור פרטים בצד שמאל בדסקטופ; טקסט כותרת או תחילת תיאור מקוצרת, מצב רשימה ריקה, סימון חזותי למשימה שהושלמה, מצב טעינה ושגיאת רשת.
- בחירה של משימה והצגת ערכיה באזור הפרטים; בהיעדר בחירה: **"בחר משימה מהרשימה כדי לצפות בפרטיה"**. ניתן להציג שדות פרטים בהתאם לעיצוב, אך אין עדיין להציג פעולות כתיבה כאילו הן עובדות.
- דף אודות עם הסבר קצר ותפריט ניווט תואם.
- Vercel המחובר ל-GitHub עם Build/Deployment אוטומטי, כולל SPA fallback שאינו פוגע ב-`/api/*`; Preview Deployments מחוברים לפרויקט ה-Dev בלבד; הפרדת Secrets בין הסביבות.
- הרצה מקומית באמצעות `vercel dev` מול פרויקט ה-Dev, עם `.env.example` המתעד את שמות משתני הסביבה.

**תוצר מצופה:** אתר חי עם שני דפים, רשימה משותפת הנקראת מתוך PostgreSQL ותצוגת פרטי משימה נבחרת. לצורך אימות ניתן להשתמש ברשומות בדיקה שהוזנו למסד באמצעות כלי פיתוח; אין עדיין ממשק יצירת משימה.

- [x] בעת כניסה אין משימה נבחרת; בחירת שורה מציגה את פרטיה; שגיאת טעינה אינה מוצגת בטעות כרשימה ריקה.

## Milestone 2 – יצירת משימה באמצעות Modal 🟢

**שם ומטרה:** לאפשר לכל מבקר להוסיף משימה לרשימה המשותפת מקצה לקצה, באמצעות ממשק תקין ו-Validation.

**מה יש לממש:**
- כפתור **"הוסף משימה"** ו-Modal בעברית לפי `DESIGN.md`, כולל שדות כותרת, תיאור ותאריך יעד ו-Placeholders.
- ערכי פתיחה: כותרת ותיאור ריקים, תאריך יעד הוא היום המקומי וניתן לנקותו. אין שדה לבחירת סטטוס: משימה חדשה מתחילה כ"לביצוע".
- Validation בצד לקוח ובשרת: לפחות כותרת או תיאור לא ריקים אחרי `trim`, גבולות 100/2000 תווים, תאריך יעד תקין שהוא היום או בעתיד, או `null`.
- `POST /api/tasks` עם SQL פרמטרי והוספה אטומית בסוף הרשימה, כולל כללי הנעילה המשותפת לפעולות המשנות את מבנה הרשימה.
- תקרת 1,000 משימות: בשרת, בדיקה בתוך ה-Transaction של היצירה ותשובת `409` כשהרשימה מלאה; בלקוח, כפתור **"הוסף משימה"** במצב Disabled עם הודעה כשברשימה 1,000 משימות.
- סגירה ללא שמירה מבטלת את הטיוטה ללא התראה; שמירה מוצלחת סוגרת Modal, מעדכנת רשימה ובוחרת את המשימה החדשה. בשגיאה נשארים הנתונים והודעת השגיאה מופיעה בטופס.

**תוצר מצופה:** משתמש יכול להוסיף משימה דרך האתר והיא מופיעה בסוף הרשימה המשותפת ונשמרת לאורך Refresh.

**Definition of Done:**
- [x] אפשר ליצור משימה עם כותרת בלבד, עם תיאור בלבד, או עם שניהם; תאריך יעד אופציונלי.
- [x] שדות ריקים/רווחים בלבד, חריגה ממגבלות אורך ותאריך יעד בעבר נחסמים עם הודעת Validation בתוך הטופס.
- [x] התאריך הראשוני הוא היום, ניתן לנקותו, ואין בחירת שעה.
- [x] שמירה מוצלחת יוצרת **רשומה אחת** במסד, בסטטוס "לביצוע", מציגה אותה ברשימה, סוגרת Modal ובוחרת אותה כך שפרטיה מוצגים.
- [x] כשברשימה 1,000 משימות, הכפתור אינו זמין ומוצגת הודעה; בקשת יצירה ישירה ל-API נדחית ב-`409` ואינה יוצרת רשומה, גם בשתי בקשות מקבילות.
- [x] סגירה ופתיחה מחדש ללא שמירה מאפסות את הטופס; שגיאת שרת משאירה Modal וערכים ומאפשרת ניסיון חוזר.
- [x] הנתונים נראים ב-Chrome גם לאחר Refresh ובכניסה ממכשיר/חלון אחר; כל הבדיקות הקודמות עדיין עוברות.

## Milestone 3 – עריכת פרטים ומחיקת משימה 🟢

**שם ומטרה:** להשלים ניהול משימה נבחרת, כולל Inline Edit ושמירה מפורשת ומחיקה עם אישור.

**מה יש לממש:**
- אזור פרטי משימה המציג מיד שדות **כותרת**, **תיאור** ו-**תאריך יעד** ניתנים לעריכה; לחצני **"שמור שינויים"** ו-**"מחק משימה"**.
- `PATCH /api/tasks/:id` לעדכון שלושת שדות הפרטים בלבד (לא `completed` או `position`); Validation כמו ביצירה, אלא שהכלל "תאריך יעד לא יכול להיות בעבר" חל רק כאשר התאריך שונה מהערך השמור.
- טיוטת עריכה בזיכרון בלבד; מעבר למשימה אחרת, מעבר דף או Refresh מבטלים שינויים שלא נשמרו ללא התראה.
- Modal אישור מחיקה לפי `DESIGN.md`, `DELETE /api/tasks/:id`, ואיפוס אזור הפרטים לאחר הצלחה.
- טיפול בכשלים בכתיבה, במשימה שנמחקה בינתיים (`404`) ובכלל `last write wins` בעדכון פרטים; אין מנגנון פתרון התנגשויות.

**תוצר מצופה:** ניתן לבחור משימה, לשנות ולשמור פרטיה, לבטל שינויים באמצעות מעבר ללא שמירה, ולמחוק אותה לאחר אישור.

**Definition of Done:**
- [x] עריכת כותרת/תיאור/תאריך ושמירה שומרות ב-Database ורואים את התוצאה לאחר Refresh.
- [x] משימה שתאריך היעד השמור שלה כבר עבר ניתנת לעריכה ולשמירה בלי לשנות את התאריך; שינוי התאריך לתאריך אחר בעבר נחסם.
- [x] בחירה במשימה אחרת, מעבר לאודות או Refresh ללא שמירה מבטלים את הטיוטה ללא התראה.
- [x] כישלון שמירה או Validation לא תקין מציגים שגיאה ומשאירים את תוכן העריכה ללא שינוי.
- [x] לחיצה על **"מחק משימה"** פותחת אישור; **"ביטול"** משאיר אותה; **"אישור"** מוחק רק לאחר הצלחת השרת.
- [x] לאחר מחיקה מוצלחת המשימה נעלמת ואזור הפרטים חוזר להודעת הבחירה; כישלון מחיקה אינו מסיר אותה מהתצוגה כאילו נמחקה.
- [x] בבדיקה של שמירות מקבילות לפרטי אותה משימה השמירה האחרונה בשרת קובעת; אין דריסה עקיפה של סטטוס או סדר.
- [x] מראה השדות וה-Modal תואם את `DESIGN.md`, ובדיקות ה-Milestones הקודמים עוברות.

## Milestone 4 – סטטוס ביצוע וסדר ידני 🟢

**שם ומטרה:** להשלים ניהול הרשימה המשותפת באמצעות Checkbox ו-Drag & Drop, כולל שמירת סדר עקבית בין מבקרים.

**מה יש לממש:**
- Checkbox בכל שורה; `PATCH /api/tasks/:id/status` ששומר מיד את הערך המפורש ומאפשר גם החזרה מ"הושלמה" ל"לביצוע".
- טקסט חצוי/סימון מתאים למשימות שהושלמו, בלי להזיז אותן או לחלק את הרשימה לקבוצות.
- סימון השלמה או גרירה של המשימה הנבחרת אינם מאפסים ואינם שומרים שינויים שלא נשמרו באזור הפרטים.
- Drag Handle ו-`dnd-kit` לסידור שורות בעכבר ובמגע ב-Android; `PUT /api/tasks/order` עם רשימת המזהים השלמה.
- Transactions, Advisory Lock משותף, נרמול `position` ואימות קבוצת המזהים למניעת אובדן או כפילות בעת יצירה/מחיקה/גרירה במקביל.
- טיפול בכישלון שינוי סטטוס או סדר: החזרת ה-UI לערך הידוע האחרון והודעה מתאימה. במקרה של `409` אין לדרוס את הרשימה; מוצגת אפשרות לרענן.
- שמירת מצב תצוגה ללא Polling/Real-Time: פעולות מבקר אחר נראות לאחר כניסה מחדש לדף הבית או Refresh.

**תוצר מצופה:** רשימה יחידה שניתן לסמן ולסדר ידנית בדסקטופ ובמובייל; כל השינויים נשמרים במסד הנתונים לכל המבקרים.

**Definition of Done:**
- [x] Checkbox מסמן ומבטל השלמה, השינוי נשמר מיד ולא משנה את מיקום המשימה.
- [x] משימות שהושלמו נשארות באותה רשימה וניתנות לגרירה כמו אחרות.
- [x] סימון Checkbox או גרירה של המשימה הנבחרת בזמן עריכה שלא נשמרה משאירים את הטיוטה באזור הפרטים כפי שהיא.
- [x] Drag & Drop עובד ב-Chrome Desktop וב-Chrome Android באמצעות Touch בלי להפעיל בטעות Checkbox או בחירת משימה.
- [x] אחרי גרירה ו-Refresh, נשמר הסדר המדויק במסד והמשימות מופיעות במיקומים רציפים ללא כפילויות.
- [x] בדיקות Integration, מול פרויקט ה-Dev, מאמתות Transaction אטומית ביצירה/מחיקה בזמן שינוי סדר ובשתי גרירות מקבילות.
- [x] אם קבוצת מזהי המשימות השתנתה לפני גרירה, השרת מחזיר `409` והלקוח אינו מאבד משימה או מחיל סדר חלקי.
- [x] תקלה בשרת מחזירה את ה-Checkbox/הסדר למצב השמור האחרון, תוך חיווי שגיאה.
- [x] שינויים של מבקר אחר מופיעים לאחר Refresh/כניסה מחדש; אין עדכוני רקע אוטומטיים, וכל היכולות הקודמות ממשיכות לעבוד.

## Milestone 5 – התאמה חזותית, PWA ובדיקת מוצר מלאה 🟢

**שם ומטרה:** להשלים חוויית שימוש מעוצבת ועקבית במובייל ובדסקטופ, ולהנגיש התקנת PWA ב-Chrome Android, ללא עבודה Offline.

**מה יש לממש:**
- השלמת עיצוב שני הדפים ומצבי ה-Modal בהתאם ל-`DESIGN.md`: צבעים, Typography, רכיבי UI, RTL, מרווחים, מצבי בחירה/שגיאה וניווט; ללא תוספות שהופיעו ב-Mockups אך אינן ב-PRD.
- ליטוש ה-Responsive שנבנה ב-Milestone 1: התאמה סופית של Modal, שדות, לחצנים ופעולות מגע ל-Viewport צר.
- Web App Manifest, אייקונים נדרשים, HTTPS ו-Standalone Display לתמיכה בהתקנת PWA ב-Chrome Android.
- מניעת Offline Cache למשימות/תשובות API ושמירת טיוטות; שגיאות רשת ברורות ואין פעולות נתונים בהיעדר חיבור.
- בדיקות אוטומטיות ומעשיות של ה-User Flows מקצה לקצה, רגרסיה, Validation, שגיאות שרת, התנהגות במספר חלונות ודפדפני Chrome הנתמכים.
- אימות Deployment ב-Production והפרדה בין סביבות הבדיקה למסד הנתונים הפעיל לפי `ARCHITECTURE.md`.

**תוצר מצופה:** מוצר TODO List שלם, בעיצוב הסופי, זמין ב-HTTPS בדסקטופ וב-Android Chrome, וניתן להתקנה כ-PWA במכשיר נתמך.

**Definition of Done:**
- [x] דף הבית ודף אודות תואמים את ה-Wireframes ואת ה-Style Guide; אין רכיבי UI פונקציונליים נוספים מעבר ל-PRD.
- [x] RTL, תצוגת תאריכים, כותרות, תוויות והודעות בעברית תקינים; בדסקטופ ובמובייל הפריסה תואמת את הדרישות.
