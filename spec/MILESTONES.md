# MILESTONES – אתר TODO List משותף

**מסמכי מקור:** `PRD.md`, `ARCHITECTURE.md`, `DESIGN.md`  
**מטרה:** חלוקת פיתוח האתר ל-Milestones ניתנים לבדיקה ולאישור, בדגש על Vertical Slices.

## כללי ביצוע הפיתוח – Development Execution Rules

1. יש לפתח את ה-Milestones **לפי הסדר** המופיע להלן. אין לדלג על אבן דרך או להתחיל אבן דרך מאוחרת טרם אישור קודמתה.
2. בסיום כל Milestone יש **לעצור את הפיתוח**, להציג למשתמש את התוצר העובד, לפרט אילו בדיקות בוצעו ולהציג את תוצאותיהן מול כל סעיף ב-**Definition of Done**. יש לציין במפורש כל בדיקה שלא בוצעה או כל תנאי שלא הושלם.
3. **אין להתחיל בפיתוח ה-Milestone הבא ללא אישור מפורש של המשתמש.** תיקונים הנדרשים לצורך עמידה ב-Definition of Done שייכים לאותה אבן דרך.
4. אין להוסיף פיצ'רים או לשנות את ה-PRD, ה-ARCHITECTURE או ה-DESIGN ללא אישור. כאשר יש סתירה בין דוגמאות חזותיות לבין הדרישות, יש לפעול לפי סדר הקדימויות שב-`DESIGN.md`.
5. כל Milestone יותיר את מה שכבר פותח במצב עובד וניתן לבדיקה; יש לבצע בדיקות רגרסיה מתאימות על היכולות הקודמות.
6. סעיפי Definition of Done שתחת הכותרת **"לאחר הדחיפה"** אפשר לבדוק רק באתר החי, ולכן הם נבדקים מיד לאחר הדחיפה שמאשרת את ה-Milestone. אם אחד מהם נכשל: מדווחים למשתמש, ה-Milestone חוזר ל-🟡, והתיקון שייך לו; אין להתחיל את ה-Milestone הבא עד שכל הסעיפים עוברים.

## Milestone 1 – יסודות המערכת וצפייה ברשימה משותפת (מקומית, מול Dev) ✅

**שם ומטרה:** הקמת האפליקציה כך שהיא רצה מקומית ומציגה רשימת משימות מתוך Database אמיתי בפרויקט ה-Dev; זהו Slice ראשון מקצה לקצה, עם תשתית להמשך CRUD. הפריסה לאתר חי שייכת ל-Milestone 2.

**מה יש לממש:**
- פרויקט React + TypeScript + Vite, ניווט לשני הנתיבים `/` ו-`/about`, CSS בסיסי בעברית RTL, כולל פריסה Responsive: שני אזורים זה לצד זה בדסקטופ, ועמודה אחת (רשימה מעל פרטים) במובייל.
- פרויקט Supabase **Dev** (ה-Data API כבוי), ובו משתמש `app_backend` שהמשתמש יוצר ידנית **לפני** החלת ה-Migration הראשונה (לפי `ARCHITECTURE.md`, ADR-2).
- טבלת `tasks` ו-Constraints בהתאם ל-`ARCHITECTURE.md`, כ-Database Migrations ב-Git המוחלות על Dev באמצעות Supabase CLI; הפרדה מאובטחת של פרטי הגישה.
- קובץ נתוני בדיקה `supabase/dev-seed.sql` עם מספר משימות לדוגמה (עם כותרת, בלי כותרת, עם תיאור ארוך, שהושלמה), שניתן להריץ מחדש על Dev בלבד.
- Vercel Functions ב-Node.js/TypeScript, חיבור מוצפן דרך Pooler עם אימות תעודת ה-CA של Supabase (`certs/supabase-ca.crt`, שהמשתמש מוריד מלוח הבקרה; ADR-3) ו-`GET /api/tasks` שמחזיר נתונים לפי `position`.
- דף הבית עם Header וניווט, רשימת משימות בצד ימין ואזור פרטים בצד שמאל בדסקטופ; טקסט כותרת או תחילת תיאור מקוצרת, מצב רשימה ריקה, סימון חזותי למשימה שהושלמה, מצב טעינה ושגיאת רשת, בנוסחים שב-PRD.
- בחירה של משימה והצגת ערכיה באזור הפרטים; בהיעדר בחירה: **"בחר משימה מהרשימה כדי לצפות בפרטיה"**. במובייל, בחירת משימה גוללת את הדף לאזור הפרטים. ניתן להציג שדות פרטים בהתאם לעיצוב, אך אין עדיין להציג פעולות כתיבה כאילו הן עובדות.
- דף אודות עם הסבר קצר ותפריט ניווט תואם.
- SPA fallback שאינו פוגע ב-`/api/*`.
- הרצה מקומית באמצעות `vercel dev` מול פרויקט ה-Dev, עם `.env.example` המתעד את שמות משתני הסביבה.

**תוצר מצופה:** אתר שרץ מקומית עם שני דפים, רשימה משותפת הנקראת מתוך PostgreSQL ב-Dev ותצוגת פרטי משימה נבחרת. לצורך אימות משתמשים בנתוני הבדיקה שב-`dev-seed.sql`; אין עדיין ממשק יצירת משימה.

**Definition of Done:**
- [ ] `GET /api/tasks` מחזיר משימות ממסד הנתונים בסדר קבוע; רשימה ריקה מחזירה `[]`.
- [ ] דף הבית מציג כותרת או תיאור מקוצר במקרה שאין כותרת; משימה שהושלמה מובחנת חזותית.
- [ ] בעת כניסה אין משימה נבחרת; בחירת שורה מציגה את פרטיה, ובמובייל הדף נגלל אליהם; שגיאת טעינה אינה מוצגת בטעות כרשימה ריקה.
- [ ] מעבר בין **דף הבית** ל-**אודות**, כולל Refresh ב-`/about`, פועל.
- [ ] מבנה המסכים תואם את ה-Wireframes בדסקטופ ובמובייל (רשימה מעל פרטים במסך צר), עם צבעי הבסיס והגופנים מה-Style Guide; הליטוש החזותי המלא שייך ל-Milestone 6.
- [ ] לאחר שינוי נתוני בדיקה במסד, Refresh בדפדפן מחזיר את הרשימה העדכנית; הנתונים אינם מאוחסנים ב-Local Storage.
- [ ] פרטי חיבור ל-Database אינם נחשפים בקוד לקוח או ב-Git; החיבור למסד מאמת את תעודת השרת ונכשל מול תעודה שגויה; Migrations מתועדות, הוחלו על פרויקט ה-Dev וניתנות להרצה מחדש עליו.
- [ ] האתר רץ מקומית מול פרויקט ה-Dev, והבדיקות הראשוניות לטעינה ולניווט עוברות ב-Chrome.

## Milestone 2 – פריסה לאתר חי (Vercel ו-Production) ✅

**שם ומטרה:** להעלות את מה שנבנה ב-Milestone 1 לכתובת ציבורית ב-HTTPS, עם מסד Production נפרד, כך שמכאן והלאה כל דחיפה לגיטהאב מעדכנת את האתר החי אוטומטית. אין שינוי פונקציונלי באתר.

**מה יש לממש:**
- פרויקט Supabase **Production** (ה-Data API כבוי), ובו משתמש `app_backend` שהמשתמש יוצר ידנית **לפני הדחיפה הראשונה**; אחרת ה-Migration שמחילה הרשאות עליו תיכשל ב-Production (ADR-2).
- חיבור פרויקט ה-Production ל-Repository באמצעות Supabase GitHub Integration עם *Deploy to production* (ADR-1). ה-CLI במחשב הפיתוח נשאר מקושר ל-Dev בלבד.
- פרויקט Vercel המחובר ל-GitHub, עם משתני הסביבה של Production בלבד ב-Vercel, Build אוטומטי בכל Push לענף הראשי ו-SPA fallback שאינו פוגע ב-`/api/*`.
- Claude מכין את קובצי ההגדרה הנדרשים ואת רשימת הצעדים; את פתיחת החשבונות וחיבור השירותים המשתמש מבצע בעצמו בהדרכה צעד אחר צעד.

**תוצר מצופה:** אתר חי בכתובת ציבורית עם שני הדפים, שקורא מ-Production, ותהליך שבו Push לענף הראשי מעדכן את האתר ואת מבנה המסד ללא פעולה ידנית.

**Definition of Done:**

לפני הדחיפה:
- [ ] Build של Production עובר מקומית, וה-SPA fallback ונתיבי ה-API נבדקו ב-`vercel dev`.
- [ ] המשתמש אישר שבוצעו: יצירת `app_backend` ב-Production, חיבור Production ל-GitHub Integration והגדרת משתני הסביבה ב-Vercel.
- [ ] פרטי Production אינם נמצאים בקוד, ב-Git או ב-`.env` המקומי; Production אינו משמש לפיתוח או לבדיקות כתיבה.

לאחר הדחיפה:
- [ ] Vercel יצר Deployment תקין, והאתר זמין בכתובת ציבורית ב-HTTPS.
- [ ] ה-Migrations הוחלו על Production אוטומטית, ללא פעולה ידנית.
- [ ] דף הבית נטען מ-Production (רשימה ריקה מוצגת כמצב ריק תקין), וניווט ו-Refresh ב-`/about` פועלים ב-Chrome; מול Production בוצעו בדיקות קריאה בלבד.

## Milestone 3 – יצירת משימה באמצעות Modal ✅

**שם ומטרה:** לאפשר לכל מבקר להוסיף משימה לרשימה המשותפת מקצה לקצה, באמצעות ממשק תקין ו-Validation.

**מה יש לממש:**
- כפתור **"הוסף משימה"** ו-Modal בעברית לפי `DESIGN.md`, כולל שדות כותרת, תיאור ותאריך יעד ו-Placeholders בנוסחים שב-PRD.
- ערכי פתיחה: כותרת ותיאור ריקים, תאריך יעד הוא היום המקומי וניתן לנקותו. אין שדה לבחירת סטטוס: משימה חדשה מתחילה כ"לביצוע".
- Validation בצד לקוח ובשרת: לפחות כותרת או תיאור לא ריקים אחרי `trim`, גבולות 100/2000 תווים, תאריך יעד תקין שהוא היום או בעתיד (לפי שעון ישראל בשרת), או `null`.
- `POST /api/tasks` עם SQL פרמטרי והוספה אטומית בסוף הרשימה, כולל כללי הנעילה המשותפת לפעולות המשנות את מבנה הרשימה.
- תקרת 1,000 משימות: בשרת, בדיקה בתוך ה-Transaction של היצירה ותשובת `409` כשהרשימה מלאה; בלקוח, כפתור **"הוסף משימה"** במצב Disabled עם הודעה כשברשימה 1,000 משימות.
- סגירה ללא שמירה מבטלת את הטיוטה ללא התראה; שמירה מוצלחת סוגרת Modal, מעדכנת רשימה, בוחרת את המשימה החדשה וגוללת אליה (ובמובייל – לאזור הפרטים). בשגיאה נשארים הנתונים והודעת השגיאה מופיעה בטופס.

**תוצר מצופה:** משתמש יכול להוסיף משימה דרך האתר והיא מופיעה בסוף הרשימה המשותפת ונשמרת לאורך Refresh.

**Definition of Done:**
- [ ] אפשר ליצור משימה עם כותרת בלבד, עם תיאור בלבד, או עם שניהם; תאריך יעד אופציונלי.
- [ ] שדות ריקים/רווחים בלבד, חריגה ממגבלות אורך ותאריך יעד בעבר נחסמים עם הודעת Validation מתחת לשדה הרלוונטי, בנוסח שב-PRD.
- [ ] התאריך הראשוני הוא היום, ניתן לנקותו, ואין בחירת שעה.
- [ ] שמירה מוצלחת יוצרת **רשומה אחת** במסד, בסטטוס "לביצוע", בסוף הרשימה; מציגה אותה, סוגרת Modal, בוחרת אותה וגוללת אליה כך שהיא ופרטיה גלויים, גם ברשימה ארוכה ובמובייל.
- [ ] כשברשימה 1,000 משימות, הכפתור אינו זמין ומוצגת הודעה; בקשת יצירה ישירה ל-API נדחית ב-`409` ואינה יוצרת רשומה, גם בשתי בקשות מקבילות.
- [ ] סגירה ופתיחה מחדש ללא שמירה מאפסות את הטופס; שגיאת שרת משאירה Modal וערכים ומאפשרת ניסיון חוזר.
- [ ] הנתונים נראים ב-Chrome גם לאחר Refresh ובכניסה ממכשיר/חלון אחר; כל הבדיקות הקודמות עדיין עוברות.

## Milestone 4 – עריכת פרטים ומחיקת משימה ✅

**שם ומטרה:** להשלים ניהול משימה נבחרת, כולל Inline Edit ושמירה מפורשת ומחיקה עם אישור.

**מה יש לממש:**
- אזור פרטי משימה המציג מיד שדות **כותרת**, **תיאור** ו-**תאריך יעד** ניתנים לעריכה; לחצני **"שמור שינויים"** ו-**"מחק משימה"**.
- `PATCH /api/tasks/:id` לעדכון שלושת שדות הפרטים בלבד (לא `completed` או `position`); Validation כמו ביצירה, אלא שהכלל "תאריך יעד לא יכול להיות בעבר" חל רק כאשר התאריך שונה מהערך השמור.
- טיוטת עריכה בזיכרון בלבד; מעבר למשימה אחרת, מעבר דף או Refresh מבטלים שינויים שלא נשמרו ללא התראה.
- Modal אישור מחיקה לפי `DESIGN.md`, `DELETE /api/tasks/:id`, ואיפוס אזור הפרטים לאחר הצלחה.
- טיפול בכשלים בכתיבה ובכלל `last write wins` בעדכון פרטים; אין מנגנון פתרון התנגשויות.
- משימה שנמחקה בינתיים בידי מבקר אחר (`404` בשמירה או במחיקה): המשימה מוסרת מהרשימה, אזור הפרטים חוזר למצב ללא בחירה ומוצגת הודעה, לפי ה-PRD.

**תוצר מצופה:** ניתן לבחור משימה, לשנות ולשמור פרטיה, לבטל שינויים באמצעות מעבר ללא שמירה, ולמחוק אותה לאחר אישור.

**Definition of Done:**
- [ ] עריכת כותרת/תיאור/תאריך ושמירה שומרות ב-Database ורואים את התוצאה לאחר Refresh.
- [ ] משימה שתאריך היעד השמור שלה כבר עבר ניתנת לעריכה ולשמירה בלי לשנות את התאריך; שינוי התאריך לתאריך אחר בעבר נחסם.
- [ ] בחירה במשימה אחרת, מעבר לאודות או Refresh ללא שמירה מבטלים את הטיוטה ללא התראה.
- [ ] כישלון שמירה או Validation לא תקין מציגים שגיאה ומשאירים את תוכן העריכה ללא שינוי.
- [ ] לחיצה על **"מחק משימה"** פותחת אישור; **"ביטול"** משאיר אותה; **"אישור"** מוחק רק לאחר הצלחת השרת.
- [ ] לאחר מחיקה מוצלחת המשימה נעלמת ואזור הפרטים חוזר להודעת הבחירה; כישלון מחיקה אינו מסיר אותה מהתצוגה כאילו נמחקה.
- [ ] שמירה או מחיקה של משימה שנמחקה בחלון אחר מסירה אותה מהרשימה, מאפסת את אזור הפרטים ומציגה את ההודעה "המשימה כבר לא קיימת".
- [ ] בבדיקה של שמירות מקבילות לפרטי אותה משימה השמירה האחרונה בשרת קובעת; אין דריסה עקיפה של סטטוס או סדר.
- [ ] מראה השדות וה-Modal תואם את `DESIGN.md`, ובדיקות ה-Milestones הקודמים עוברות.

## Milestone 5 – סטטוס ביצוע וסדר ידני ✅

**שם ומטרה:** להשלים ניהול הרשימה המשותפת באמצעות Checkbox ו-Drag & Drop, כולל שמירת סדר עקבית בין מבקרים.

**מה יש לממש:**
- Checkbox בכל שורה; `PATCH /api/tasks/:id/status` ששומר מיד את הערך המפורש ומאפשר גם החזרה מ"הושלמה" ל"לביצוע".
- טקסט חצוי/סימון מתאים למשימות שהושלמו, בלי להזיז אותן או לחלק את הרשימה לקבוצות.
- סימון השלמה או גרירה של המשימה הנבחרת אינם מאפסים ואינם שומרים שינויים שלא נשמרו באזור הפרטים.
- Drag Handle ו-`dnd-kit` לסידור שורות בעכבר ובמגע ב-Android וב-iPhone; `PUT /api/tasks/order` עם רשימת המזהים השלמה.
- Transactions, Advisory Lock משותף, נרמול `position` ואימות קבוצת המזהים למניעת אובדן או כפילות בעת יצירה/מחיקה/גרירה במקביל.
- טיפול בכישלון שינוי סטטוס או סדר: החזרת ה-UI לערך הידוע האחרון והודעה מתאימה. במקרה של `409` אין לדרוס את הרשימה; מוצגת אפשרות לרענן.
- שמירת מצב תצוגה ללא Polling/Real-Time: פעולות מבקר אחר נראות לאחר כניסה מחדש לדף הבית או Refresh.

**תוצר מצופה:** רשימה יחידה שניתן לסמן ולסדר ידנית בדסקטופ ובמובייל; כל השינויים נשמרים במסד הנתונים לכל המבקרים.

**Definition of Done:**
